# Voxel-SLAM 建图—定位初始版本设计基线

**日期：** 2026-10-06
**状态：** 已实现的第一版基线，用于后续空间体素块改造前的版本固化。
**适用分支：** `main`

## 1. 目标与边界

本版本在原始 Voxel-SLAM 基础上增加建图地图包、跨 Session 重定位和只读历史地图连续定位能力。

主要目标：

1. 建图结束后保存最终优化的融合关键帧、BTC 描述子帧和几何验证平面云；
2. 定位启动后加载历史地图，通过 BTC、点到面 ICP 和 GTSAM 将当前 Session 对齐到 `map` 坐标系；
3. 重定位成功后，以历史关键帧点云构建只读局部体素地图，通过 LiDAR-IMU IESKF 连续定位；
4. 支持 YAML 二维位置先验限制 BTC 候选范围，以及 RViz `/initialpose` 直接初始化；
5. 定位质量持续不合格时进入 `LOST`，保留历史地图并重新执行 BTC 重定位。

本版本不包含预构建空间体素块。连续定位地图仍以历史关键帧作为加载和卸载单位。

## 2. 双运行模式

### 2.1 建图模式

建图模式继续运行原始 Voxel-SLAM 的：

- LiDAR-IMU 初始化和 IESKF；
- 滑动窗口 LBA；
- BTC 回环；
- GTSAM 位姿图优化；
- 必要时的全局 BA。

满足运动阈值时，将多 Scan 融合结果保存为关键帧。地图导出必须在最终回环和全局优化结束后执行，以最终关键帧位姿作为地图坐标系表达。

### 2.2 定位模式

定位模式加载不可变历史地图包。重定位成功前，当前 Session 在临时 `odom` 坐标系中独立运行 LIO；成功后对前端状态施加全局修正，并切换到历史地图只读跟踪。

定位过程中：

- 不把当前扫描写入历史固定地图；
- 不修改历史关键帧位姿；
- 不运行会改变历史地图的 GBA；
- 不写回历史地图包。

## 3. 地图包内容

地图包保存：

- 地图格式版本和坐标系约定；
- 关键参数摘要；
- 最终融合关键帧位姿；
- 关键帧局部坐标系点云；
- BTC 描述子数据库；
- BTC 帧到锚点关键帧的显式映射；
- BTC 几何验证平面云。

关键帧点云、BTC 顶点和验证平面云均保存在各自锚点关键帧局部坐标系中，加载后再通过最终位姿转换到 `map` 坐标系。

## 4. BTC 重定位

### 4.1 无先验全局 BTC

当 `Localization/use_prior_pose_for_btc=false` 时，当前融合关键帧生成 BTC 查询描述子，并在全部历史 BTC 帧中检索候选。

### 4.2 二维位置先验 BTC

当 `Localization/use_prior_pose_for_btc=true` 时：

1. 从 YAML 读取先验 `x/y`；
2. 在历史关键帧二维位置 KD-Tree 中查询指定半径内关键帧；
3. 将关键帧 ID 转换为允许参与检索的 BTC 帧集合；
4. `SearchLoop()` 在描述子投票阶段忽略允许集合之外的历史帧；
5. 失败时按配置逐级扩大半径；
6. 达到最大半径后可回退到全局 BTC。

BTC 范围选择不使用 yaw 约束。

### 4.3 候选验证与 Session 对齐

BTC 候选必须经过：

- BTC 自带平面几何验证；
- 点到面 normal ICP；
- 最低匹配分数；
- 法向可观测性检查；
- 变换有限性和安全门限。

通过后，以历史关键帧为固定锚点，通过 GTSAM 优化当前 Session 轨迹，得到临时 `odom` 到 `map` 的全局修正。提交结果前检查前端 Session 代数，过期异步结果不得覆盖已经复位的前端。

## 5. RViz 直接初始化

系统订阅标准 `/initialpose`：

- `x/y/yaw` 来自 RViz；
- `roll/pitch` 来自已经完成初始化的 IMU；
- `z` 取二维距离最近的历史关键帧高度。

RViz 路径跳过 BTC，但不能直接进入有效定位状态。系统先在该位姿附近构建历史局部地图，连续若干 Scan 通过点到面匹配质量验证后，才将 `localization_valid` 置为真。

RViz 请求优先于尚未提交的 BTC 结果。验证失败后清理临时状态，并恢复配置指定的 BTC 重定位流程。

## 6. 历史关键帧空间索引

地图加载时一次性建立两个 PCL KD-Tree：

- 二维 `x/y` 索引：用于 BTC 先验范围查询和 RViz 最近高度查询；
- 三维 `x/y/z` 索引：用于连续定位的历史关键帧动态加载。

索引点与关键帧 ID 通过显式数组映射，不能假设 KD-Tree 返回下标等于关键帧 ID。

KD-Tree 只保存关键帧位置，不保存完整关键帧点云，也不参与 IESKF 点到面平面查询。历史地图不可变，因此定位过程中不重建关键帧 KD-Tree。

## 7. 初始版本的局部体素地图维护

### 7.1 首次构建

BTC 或 RViz 得到候选全局位姿后，以该位置为中心在历史关键帧三维 KD-Tree 中执行半径查询，按距离排序并预加载最多 `local_map_preload_limit` 个关键帧。

所有活动关键帧点云通过最终位姿变换到 `map` 坐标系，然后重新构建固定历史 `surf_map`。

### 7.2 连续更新

每个定位 Scan 在 IESKF更新前：

1. 使用 IMU 传播后的预测位置查询 `local_map_load_radius` 内历史关键帧；
2. 每 Scan 最多新增 `local_map_max_load_per_scan` 帧；
3. 已加载但距离超过 `local_map_unload_radius` 的关键帧从活动集合移除；
4. 加载半径和卸载半径形成滞回，避免边界抖动；
5. 如果活动集合没有变化，复用现有 `surf_map`；
6. 如果活动集合发生变化，使用全部剩余活动关键帧完整重建 `surf_map`。

### 7.3 体素地图结构

`surf_map` 是：

```cpp
std::unordered_map<VOXEL_LOC, OctoTree *>;
```

顶层哈希表保存稀疏体素坐标，每个顶层体素对应一个局部 `OctoTree`。`OctoTree` 根据平面性自适应细分，叶节点主要保存：

- `PointCluster` 充分统计量 `N/Σp/Σppᵀ`；
- 点云质心和协方差特征值、特征向量；
- 平面中心、法向、覆盖范围和不确定性；
- 八叉树拓扑和体素空间信息。

IESKF 将当前激光点变换到 `map` 坐标系，通过顶层体素哈希和局部 `OctoTree` 查找有效平面，构造点到面残差。

## 8. 定位状态机

主要状态包括：

```text
WAITING_FOR_MAP
LOCAL_ODOMETRY
RELOCALIZING
ALIGNING
IN_MAP_TRACKING
LOST
```

连续定位监控：

- 匹配点数量；
- 平均点到面绝对残差；
- 法向散布最小特征值；
- 解和状态是否有限；
- 连续坏帧计数。

达到丢失条件后清理当前 Session 和运行时局部地图，但保留地图包、历史 BTC 数据库和历史关键帧 KD-Tree，随后重新进入 BTC 重定位。

## 9. 当前版本的已知限制

### 9.1 活动关键帧变化会完整重建体素地图

历史固定点融合进入 `PointCluster` 和平面后，没有保存每个关键帧对每个体素的独立贡献。系统无法只减去一个关键帧的统计量，因此加载或卸载关键帧时只能使用全部活动关键帧重新体素化、重新构建 OctoTree 和重新计算平面。

该过程在里程计线程中同步执行，是当前大规模地图实时性的主要风险。

### 9.2 地图管理单位和匹配单位不一致

- 加载和卸载单位：历史关键帧；
- IESKF 查询单位：空间体素和平面。

关键帧由建图轨迹决定，空间覆盖不规则；往返或多次经过同一区域时，附近可能存在大量重复关键帧。

### 9.3 缺少运行时性能实测

当前代码在 Windows 上完成静态检查和不依赖 ROS 的测试，但尚未在 Ubuntu 20.04、ROS Noetic 和目标激光雷达数据上完成编译及实时性验证。

后续必须测量：

- KD-Tree查询时间；
- 活动关键帧和活动点数量；
- 世界坐标变换时间；
- 体素地图重建时间；
- IESKF时间；
- 单帧总时间的平均值、P95和最大值；
- CPU和内存占用。

## 10. 后续空间体素块改造边界

下一版本保留本版本的：

- 关键帧/BTC地图持久化；
- 全局和先验约束BTC检索；
- ICP与GTSAM对齐；
- RViz直接初始化；
- 定位状态机、质量监控和LOST恢复。

只替换连续定位参考地图的组织方式：在最终优化后，将多关键帧观测离线融合为独立、不可变、可序列化的空间体素块。定位时按空间增量加载和卸载预构建块，不再因历史关键帧集合变化而完整重建局部体素地图。
